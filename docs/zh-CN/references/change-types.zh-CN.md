# 变更类型

每个动作只指定一个主要类型。一个项目可以同时需要多种变更，但每项变更都应有明确的责任方和依赖顺序。

| 类型 | 适用情况 | 所需证据 |
|---|---|---|
| 删除 | 逻辑、状态、UI 或术语错误、过时、重复，或已被替代 | 删除后，调用方和必须保留的行为仍有覆盖 |
| 重构 | 正确行为已经存在，但责任、状态或策略四处分散 | 所有相关入口都由同一个权威来源或统一边界承接 |
| 实现 | 承诺的能力或可强制执行的行为尚不存在 | 一条真实端到端路径能够生成并持久保存预期结果 |
| 隐藏 | 内部细节对高级操作仍有价值，但不属于普通用户工作 | 用户无需理解内部对象也能完成正常流程 |
| 文案修改 | 结构和行为正确，但语言错误表达了含义或下一步 | 用户能够正确理解当前状态并采取正确行动 |
| UI 优化 | 结构、行为和语言都正确，只剩层级或视觉一致性问题 | 视觉与交互检查通过，且没有用表面效果掩盖结构缺陷 |

## 分类检查

- 当前路径本就不该存在：**删除**。
- 多条路径应该收敛到同一个权威来源：**重构**。
- 系统只是在模拟或口头承诺能力：**实现**。
- 操作者仍需细节，但普通用户不需要：放到高级边界后面并**隐藏**。
- 行为正确，只有含义表达不清：**文案修改**。
- 含义和行为都正确，只剩呈现问题：**UI 优化**。

## 依赖顺序

多种变更互相影响时，默认使用这个顺序：

~~~text
删除过时路径
  -> 重构责任归属与唯一事实源
  -> 实现缺失能力
  -> 隐藏内部复杂度
  -> 修正文案
  -> 优化 UI
~~~

如果证据要求改变顺序，要明确说明是哪项依赖关系支持这个例外。

## 混合症状示例

过时的上传面板属于删除。两套输入框分别保存草稿属于重构。声称能读 PDF、实际没有接入读取能力属于实现。正常流程中的原始 Job Payload 应该隐藏。用户按钮上的内部术语需要修改文案。间距不一致则应等流程结构正确后再做 UI 优化。
