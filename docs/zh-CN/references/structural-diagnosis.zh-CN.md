# 结构性诊断

当故障再次出现，或系统不断累积规则、临时绕行方案和局部修补时，使用这份参考资料。

## 结构性信号

出现下列任一情况时，优先调查结构：

- 上一次修复已经通过，但用户可见的故障再次出现。
- 新方案又要增加一条禁令、特殊分支或同步规则。
- 用户或操作者必须记住一个临时绕行办法。
- 两个入口或界面对同一事实给出不同结果。
- 用户必须理解内部编排，才能正常完成任务。
- 本可由代码或策略彻底禁止的错误状态，却依赖提示词去约束。
- 只修了一个入口，其他等价路径仍未改变。

结构性信号只是待验证的假设，不是判决。必须用当前源码、状态和执行证据确认。

## 诊断链

针对每个重要问题，建立以下判断：

1. **症状：**可以准确观察到的故障是什么。
2. **责任方：**哪一层、哪个对象有能力产生它。
3. **权威来源：**应由哪项策略、哪条记录或哪个组件决定事实。
4. **竞争路径：**哪些重复逻辑、状态、入口或交接可能与权威来源冲突。
5. **根因：**什么机制允许错误状态产生。
6. **预防：**移除或约束该机制的最小结构性变更是什么。
7. **证据：**哪项检查会在旧行为下失败，并在修正后通过。

必须区分观察事实和推断。如果现有证据不足以定位原因，应继续诊断，直到证据能够支持结论，而不是把结构猜测包装成事实。

## 删除与合并检查

增加新行为前，先寻找：

- 已经过时的组件或流程；
- 互相竞争的事实源；
- 被复制的策略或状态迁移；
- 没有真实执行、只会回复成功的脚本；
- 暴露在正常用户路径中的调试对象或过渡对象；
- 用补丁式条件掩盖缺失不变量的逻辑；
- 对同一个交互契约存在多份独立实现。

只有当被移除的行为错误、过时、重复，或已被权威路径替代时，删除才是正确选择。仍然承担真实用户价值或系统义务的行为必须保留。

## 更强修复检查

优先选择让错误状态难以产生、最好无法产生的变更：

- 两个界面各自刷新复制的任务状态 → 两者都从同一条权威生命周期记录生成投影。
- 只在提示词里要求模型不要暴露 Payload → 正常用户界面根本接收不到 Payload 字段。
- UI 经过计时器后就声称文件已处理 → 必须由真实执行结果驱动可见状态。

提示词或文案约束适合解决它们真正负责的沟通行为，不能替代本可由状态、策略或执行结构强制保证的设计。
