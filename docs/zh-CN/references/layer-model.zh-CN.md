# 分层模型

当需要定位责任归属和唯一事实源时，使用这份参考资料。层的名称可以根据真实系统调整；目的是明确责任，不是强迫系统服从一张固定架构图。

## 稳定分层

| 层 | 常见对象 | 责任归属问题 |
|---|---|---|
| 用户可见层 | 对话、输入、导航、输出、确认、状态 | 哪些内容必须由用户理解或操作？ |
| 对话与编排层 | 意图、路由、执行顺序、审批、模型回复 | 由谁决定下一步发生什么？ |
| 领域与策略层 | 业务规则、权限、资格条件、不变量 | 规则在哪里定义，又在哪里强制执行？ |
| 数据与状态层 | 消息、任务、作业、文件、结果、生命周期状态 | 哪一条记录才是权威事实？ |
| 执行与集成层 | 工具调用、Worker、API、文件访问、浏览器操作 | 谁真正执行外部工作？ |
| 记忆与生命周期层 | 上下文摘要、归档、恢复点、保留策略 | 工作如何恢复或审计？ |
| 验证与版本层 | 测试、契约、可观测性、发布锚点、回滚 | 什么能证明行为正确，并保留恢复能力？ |

并非每个系统都需要全部层。只有当某一层拥有独立的决策或事实源时，才增加它。

## 责任追踪

沿着这条链追踪问题：

~~~text
可见症状
  -> 交互或入口
  -> 责任层
  -> 责任组件或策略
  -> 权威状态或事实源
  -> 执行路径
  -> 验证信号
~~~

问题通常出现在可见表层，但责任未必属于那里。一个标签错误可能暴露状态错误；侧栏不一致可能暴露重复的生命周期状态；依赖人工搬运的交接可能暴露缺失的执行集成。

## 唯一事实源检查

针对每项重要事实，逐一询问：

1. 哪个对象是权威对象？
2. 哪些对象只是投影或缓存？
3. 谁可以写入权威对象？
4. 投影如何接收更新？
5. 更新延迟、重复或乱序时会发生什么？
6. 是否有两个组件都能独立声称自己说了算？

当两个界面显示不一致时，先修正权威事实源和投影路径，再改任一界面的显示。

## 表达深度

- 现有架构已经能定位责任时，直接复用。
- 其余结构稳定时，只更新受影响的分支。
- 多个问题需要填写相同字段时，使用紧凑表格。
- 关系、生命周期或交接仍有歧义时，再画树或流程图。
- 当前决策和回归边界已经可以检查时，就停止扩展。
